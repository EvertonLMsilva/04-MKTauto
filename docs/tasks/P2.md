## Uso pela aplicação existente
Construir `MediaAssetRepository` e `CostLedgerRepository` para o mesmo arquivo
SQLite privado. Injetar o segundo como `costRepository` no `FalVideoAdapter`.
O adapter é um `MediaProvider`: passar a instância ao `MediaAcquisitionService`
existente e chamar `acquire(MediaAcquisitionRequest)` com assetType VIDEO.
Não altera seleção/configuração dos providers genéricos.

Configuração do adapter: `mediaRef` do briefing, `rights` com PROVIDER_TERMS
e commercialUseAllowed true, `budget` (amount decimal positivo em texto,
currency), `estimate` (amount, currency, source auditável), `storageRoot`,
`maxVideoBytes`, `ffmpegPath`, `ffprobePath`, `apiKey` privado, limites/timeout.
`resolveImage(mediaRef)` é dependência explícita do operador: retorna URL HTTPS
da imagem autorizada e SHA-256 de seus bytes exatos. Não há upload automático.
Os testes injetam queue/storage/resolver fake; nenhum segredo é requerido.

`PROVIDER_GENERATION_PENDING` significa executar novamente a mesma aquisição
para consultar a fila. `getGenerationState(acquisitionRequestId)` expõe estado,
request ID, resultado, evento de custo, `observedCostAmount` acumulado (null =
indisponível) e `financiallySettled`. URLs válidas devolvidas pelo provider são
persistidas. URLs rejeitadas são descartadas; o ID válido permanece salvo em
RECONCILIATION_PENDING. Uma próxima aquisição pode recuperar somente via GET
nas rotas oficiais de owner/alias + request ID, validadas antes do transporte.
Referência: https://github.com/fal-ai/fal-js/blob/main/libs/client/src/queue.ts
(status/result removem o subpath do endpoint). Não há GET imediato após a
resposta parcialmente inválida nem armazenamento/log da URL rejeitada.

DISPATCHING e RECONCILIATION_PENDING sem ID exigem reconciliação humana com
evidência do provider. Não expiram para liberar POST e não há API de reset
ou fallback. FAILED também não submete novamente. Erros de consulta/download
com ID conhecido permitem novo GET da mesma solicitação.

`adapter.jobs.recordObservedCost(generationKey, { amount, currency, source,
occurredAt, final = false })` recebe custo comprovado acumulado; cada incremento
positivo vira evento imutável no CostLedger, identificado pelo hash da evidência.
Retry da mesma evidência não duplica custo; observação anterior já registrada
continua idempotente. Não há conversão da estimativa em custo.
`final: true` exige estado COMPLETED ou FAILED e evidência financeira definitiva;
registra liquidação imutável na migração 032. Conclusão técnica sozinha não
liquida. Redução do acumulado não é aceita: restituições exigem reconciliação.
Valores positivos seguem o contrato CostLedger existente.
Não se infere preço de timings nem se transforma estimativa em despesa real.
Sem liquidação definitiva, o compromisso é max(estimativa, custo acumulado),
inclusive para falha/resultado incerto. O ledger conta o custo e somente a
diferença positiva da reserva é adicionada, evitando dupla contabilização.
Após liquidação, conta apenas o custo confirmado. Nenhuma restituição é
presumida. Moedas distintas
exigem reconciliação explícita, sem conversão inventada.
